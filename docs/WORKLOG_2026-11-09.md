## 1. 프로젝트 범위를 다시 맞추기
- 목표/문제: 별도 게시판이 아니라 premium-food-api의 한정 수량 식품·회원·주문·재고·취소에 게시판을 결합해야 함.
- 접근/선택 이유: 기존 상품 4컬럼을 유지하고 선생님 4계층을 기능 내부에 적용. 결제·배송·쿠폰은 추가하지 않음.
- 수행: README/현재 수정/원격 HEAD 확인, 미커밋 파일 포함 13개 소스 SHA-256 백업, work/premium-food-board 브랜치에서 진행.
- 결과/근거: 원본 복사본 재검증. 기존 .env·실DB·원본 게시판 폴더 보존. 별도 게시판의 45개 통과는 이번 통합 증거와 구분.

## 2. 주교안과 발제문의 필수 기능 대조
- 목표/문제: ORM 실습 코드와 실제 4계층 과제를 구분하고 OAuth2·CORS/로그·Jinja2 누락 방지.
- 접근: ORM 쿼리는 infrastructure, 규칙은 domain, 순서/commit은 application, 입력/HTTP는 presentation. import 경로 premium_food_api로 통일.
- 수행: callable datetime, find_by_id 이름, 모든 모델·라우터 등록, JWT 공개 기본키 제거, 작은 TransactionManager 계약 적용.
- 결과/근거: test_architecture.py 및 앱 import. 교안 게시판 페이지는 비어 있어 GitHub 선생님 코드를 보완 출처로 명시.

## 3. 회원·인증·게시판 통합
- 목표: 회원 이름/전화/이메일/아이디/비밀번호와 이메일 로그인, 작성자 권한.
- 구현: username/email 중복 방지, bcrypt, OAuth2/JWT/블랙리스트, 본인 비밀번호 변경. 회원 ID를 주문/게시판에서 공통 사용.
- 문제 해결: 게시판에 실명 대신 공개 아이디를 표시하도록 검수 반영. 기존 JWT 전체 철회는 후속 설계로 구분.
- 근거: test_api.py, test_member_auth.py, 실제 HTTP 회원가입/로그아웃/게시글 CRUD.

## 4. 주문·재고·취소
- 문제: 상품 저장 후 주문 저장이 실패하면 재고만 차감될 수 있고, 동시 주문/취소는 단순 if 검사만으로 안전하지 않음.
- 선택: 같은 AsyncSession, repository flush, 서비스 한 번 commit/오류 rollback. 상품 ID 순 잠금, 취소할 주문 먼저 잠금. 큰 Unit of Work 프레임워크는 도입하지 않음.
- 구현: Order/OrderItem, 주문번호·일자·항목/가격 스냅샷, 소유권 검사, 재고 복구 한 번.
- 실제 확인: 실패 주입 rollback, 별도 DB 연결 동시 주문 201/409·동시 취소 200/409, stock 보존.
- 근거: orders/application/services.py, products/domain/entities.py, test_commerce.py, test_concurrency.py.

## 5. 화면·검수·문제 해결
- 구현: Jinja2 상품 목록/상세, 검색/재고/가격/정렬/페이지, CSS, CORS/시간 로그.
- 발견/해결: class의 list 메서드가 타입힌트 list를 가려 import 실패 → postponed annotations. DI 등록 줄바꿈 오류 → 구문 검사 후 수정. 검수에서 깨진 option 태그 → 실제 HTMLParser 검사 추가. commerce DI → wiring으로 통일. 동시 로그아웃 → ON CONFLICT DO NOTHING.
- Claude Code: 사용자 승인 후 소스·가상 테스트만 읽기 전용 검수 2회. 조건부 None/로그/72바이트 지적은 실제 코드와 테스트로 확인.
- 결과: 최종 93개 테스트 통과(17.74초), 기본 lint/compile/diff 검사 통과. 실제 서버 HTTP200/샘플20개/재시작 지속성 확인.
- 한계: 브라우저 연결 오류로 눈으로 본 화면과 캡처는 미완료. HTTP200만으로 화면 검증 완료라고 기록하지 않음.
